## 二、BUG-006 RUNTIME_CRASH深度分析

### 2.1 Guardian日志崩溃时间线

| # | 崩溃时间(本地) | 运行时长 | 退出码 | 信号 | crash日志 |
|---|---------------|----------|--------|------|-----------|
| 1 | 09-05 23:23 | 70秒 | 1 | null | ❌ 无 |
| 2 | 09-05 23:35 | 12分24秒 | 1 | null | ❌ 无 |
| 3 | 09-05 23:48 | 13分14秒 | 1 | null | ❌ 无 |
| 4 | 09-06 00:07 | 5分18秒 | 1 | null | ❌ 无 |

### 2.2 崩溃特征

- **退出码始终为1，信号为null**：不是被系统kill（signal会是SIGKILL/SIGTERM），而是进程主动调用`process.exit(1)`或未捕获的致命错误
- **无crash日志文件**：v4.77的uncaughtException处理器会写crash-*.log，但这些崩溃没有日志，说明崩溃路径**绕过了uncaughtException**
- **崩溃间隔不稳定**：5-13分钟，可能与负载/状态累积相关
- **Guardian自动重启正常**：每次崩溃后2-4秒内重启成功，服务可用性>99%

### 2.3 可能根因（待排查）

1. **内存泄漏导致OOM**：但Windows上OOM通常是signal=null + code=137，而非code=1
2. **某个子系统主动调用process.exit(1)**：可能是健康检查失败、断言失败、或防御性退出
3. **WebSocket/LLM连接异常**：异步错误未被uncaughtException捕获（如worker_thread崩溃）
4. **v8引擎内部错误**：罕见但可能

### 2.4 建议排查方向

1. 在server/index.js入口添加`process.on('exit', code => console.log('EXIT code=' + code))`和`process.on('beforeExit')`记录退出前状态
2. 检查所有`process.exit(`调用点，添加日志
3. 启用Node.js `--trace-uncaught`标志
4. 检查是否有worker_thread或child_process崩溃导致主进程退出
5. 监控崩溃前的内存/CPU/事件循环延迟
